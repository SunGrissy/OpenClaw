## 小马模型切换：deepseek-v4-flash → kimi-k2.6
- 原因：DeepSeek V4 Flash 默认开启 thinking 模式，OpenClaw 不支持 `thinking: {"type": "disabled"}` 参数
  - 报错：`LLM request failed: provider rejected the request schema or tool payload`
  - 根因：DeepSeek V4 返回 `reasoning_content`，OpenClaw 下轮不回传此字段 → 400
- OpenClaw 代码分析：
  - `reasoning: false` 配置只控制 `reasoning_effort` 参数，不发 `thinking` 参数
  - `supportsReasoningEffort: true` 的 compat 标记反而让 OpenClaw 尝试发 `reasoning_effort`，但 DeepSeek 要的是 `thinking`
  - 消息回传逻辑没有保留 `reasoning_content` 字段
- 解决：小马换 moonshot/kimi-k2.6（Kimi 不默认开 thinking）
- 妙妙 Hermes 也改了代码：在 run_agent.py 加了 DeepSeek thinking 模式支持（类似 Kimi 的处理），发 `extra_body.thinking = {"type": "enabled/disabled"}`
  - 改动位置：`D:\hermes\hermes-agent\run_agent.py` 第7023行后
  - 注意：妙妙当前模型是 kimi-k2.6，此改动待妙妙切到 deepseek-v4-flash 时生效

## 踩坑：DeepSeek V4 Flash thinking 模式兼容性问题

## 踩坑：OpenClaw DeepSeek 插件 vs 自定义 Provider
- 坑：OpenClaw 内置 DeepSeek 插件需要 `DEEPSEEK_API_KEY` 环境变量才能注册模型，光写 `plugins.entries.deepseek.enabled: true` 不够，模型还是报 "Unknown model"
- 坑2：插件 schema 不支持 `apiKey` 和 `env` 字段，不能在 plugins.entries.deepseek 里直接传 key
- 坑3：`openclaw onboard --auth-choice deepseek-api-key` 虽然写了配置，但 gateway port 被改回默认18789，deepseek 插件又被设为 enabled:false
- 坑4：`.env` 文件放在 `$OPENCLAW_STATE_DIR/.env` 不一定被读（可能读 `~/.openclaw/.env`）
- 绕法（最终成功）：用自定义 `models.providers.deepseek` 直连 API，`models.mode: "replace"` 替代内置 catalog，禁用插件避免冲突
  - 直接在 provider 里写 apiKey，不依赖环境变量和插件
  - `reasoning: true`（V4 支持推理！）
  - `compat.supportsReasoningEffort: true`
  - `contextWindow: 1000000` / `maxTokens: 384000`（按官方文档）
- 教训：OpenClaw 内置 provider 插件的模型注册和自定义 provider 是两套体系，混用会打架。要么全走插件（需要正确的环境变量/onboard），要么全走自定义 provider（`models.mode: "replace"`）

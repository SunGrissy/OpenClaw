# Superpowers · 开发工作流纪律

> 提炼自 [obra/superpowers](https://github.com/obra/superpowers)，保留核心纪律，适配 OpenClaw 环境。
> **纪律不是建议。** 违反字母就是违反精神。

---

## 一、技能优先律

**1% 可能相关就先查 SKILL，不许跳过。**

所有"太简单不需要""我先看看再说""这不需要正式流程"都是 red flag。

| 你在想 | 现实 |
|--------|------|
| "这只是个简单问题" | 问题是任务，查 skill |
| "我需要更多上下文" | skill 检查在澄清问题之前 |
| "让我先探索一下代码" | skill 告诉你怎么探索 |
| "这个不需要正式流程" | 简单的事变复杂最快 |
| "我记得这个 skill" | skill 会演进，读当前版本 |
| "我只想先做这一件事" | 做任何事之前先查 |

**优先级：流程 skill 先于实现 skill。** "建 X" → brainstorming → 实现 skill。"修 bug" → debugging → 领域 skill。

**类型：**
- **刚性 skill**（TDD、debugging）：严格遵循，不许变通
- **柔性 skill**（模式库）：适配原则到上下文

skill 自己会说明是哪种。

## 二、Brainstorming · 苏格拉底式设计提炼

**硬门禁：未完成设计，禁止写任何代码。** 包括"太简单不需要设计"的项目。

### 清单

1. **探索项目上下文**——检查文件、文档、近期提交
2. **逐个提问**——一次一个问题，理解目的/约束/成功标准；优先多选题
3. **提出 2-3 种方案**——带取舍和推荐
4. **分段展示设计**——按复杂度缩放每段长度，每段后确认
5. **写设计文档**——保存到 `docs/specs/` 或用户指定位置
6. **Spec 自审**——扫占位符/矛盾/歧义/范围，修完即走
7. **用户审 spec**——等用户批准才继续
8. **转入 writing-plans**——唯一允许调用的下一个 skill

### 关键原则

- **YAGNI**——所有设计中砍掉不需要的功能
- **2-3 种方案**——永远先探索替代方案
- **增量验证**——展示一段，确认一段
- **为隔离而设计**——每个单元单一职责、明确接口、可独立理解和测试

### Red Flag

- "这个太简单，不需要设计" → 最简单的项目，未审视的假设造成最大浪费
- 设计没批准就动手写码 → 违反硬门禁

## 三、Writing-Plans · 零占位符计划

**面向"零上下文初级工程师"写计划。** 每步 2-5 分钟，含完整代码，零占位符。

### 规则

- 每步是一个动作：写测试 → 跑测试确认红 → 写最小实现 → 跑测试确认绿 → 提交
- **禁占位符：** 不许出现 TBD / TODO / "后续补充" / "添加适当错误处理" / "写测试"（不给代码） / "类似 Task N"
- **DRY + YAGNI + TDD + 频繁提交**
- 每步必须含：精确文件路径、完整代码、精确命令和预期输出

### 文件结构

先定文件职责，再分解任务。每个文件一个清晰职责，一起改的文件放一起。

### 自审

1. **Spec 覆盖**：每个 spec 需求能指向一个 task
2. **占位符扫描**：搜 red flag 模式
3. **类型一致性**：跨 task 的函数签名/属性名是否对得上

### 交付

计划完成后提供两种执行选项：
1. **子 agent 驱动**（推荐）——逐任务派发，两阶段审查
2. **内联执行**——本会话批量执行，带检查点

## 四、子 Agent 驱动开发

**每个任务一个干净上下文的子 agent，完成后两阶段审查。**

### 流程

```
读取计划 → 提取全部任务 → 创建 Todo
    ↓
Per Task:
  派发实现子 agent（含完整任务文本 + 上下文，不让子 agent 自己读计划文件）
  → 实现子 agent 实现、测试、提交、自审
  → 派发 Spec 合规审查子 agent（是否多建/少建）
  → 不合规则修复 → 重审
  → 合规则派发代码质量审查子 agent（写得好不好）
  → 不通过则修复 → 重审
  → 通过则标记任务完成
    ↓
全部完成 → 最终全量代码审查 → finishing-a-development-branch
```

### 关键纪律

- **子 agent 不继承主会话上下文**——你构造它需要的信息
- **两阶段审查顺序不可颠倒**：先 spec 合规，再代码质量
- **Spec 合规审查绝不信任实现者的报告**——独立验证一切
- **3 种子 agent 角色分工**：实现者（干）、spec 审查者（查对不对）、质量审查者（查好不好）

### 模型选择

- **机械任务**（1-2 文件，spec 完整）→ 快速便宜模型
- **集成任务**（多文件，需模式匹配）→ 标准模型
- **架构/设计/审查任务** → 最强模型

### 处理子 Agent 状态

| 状态 | 处理 |
|------|------|
| DONE | 进入审查 |
| DONE_WITH_CONCERNS | 读疑虑再决定 |
| NEEDS_CONTEXT | 补充上下文重派 |
| BLOCKED | 评估阻塞：补上下文/换更强模型/拆小任务/计划有错则升级给人 |

## 五、TDD · 测试驱动开发铁律

**没有失败测试，不允许写生产代码。**

### RED-GREEN-REFACTOR

```
RED：写一个最小失败测试 → 跑测试确认红（必须看到失败）
GREEN：写最小代码让测试通过 → 跑测试确认绿
REFACTOR：清理（去重、改善命名、提取辅助） → 测试保持绿
重复
```

### 铁律

- **先写代码后补测试？删掉重写。** 不保留当"参考"，不"适配"
- **测试立即通过？** 你在测已有行为，不是新功能
- **测试报错而非失败？** 修错再跑，直到看到正确的失败
- **跳过"就这一次"？** 每次跳过都是理性化

### Red Flag → 删代码重来

- 代码写在测试之前
- "先实现后补测试"
- "这太简单不需要 TDD"
- "保留当参考再写测试"
- "TDD 会拖慢我"
- "已经手动验证过了"
- "事后测试效果一样"

**不一样。** 事后测试回答"这做了什么"，测试优先回答"这应该做什么"。偏见来自实现，不是需求。

## 六、Systematic Debugging · 系统调试四阶段

**没有找到根因，不允许修。** "快速修一下"就是失败模式。

### Phase 1: 根因调查

1. **读错误信息**——完整读，不跳过，记行号/文件/错误码
2. **稳定复现**——能可靠触发吗？步骤是什么？
3. **查近期变更**——git diff、新依赖、配置变更、环境差异
4. **多组件系统加诊断日志**——每个组件边界记录进出数据，跑一次定位断在哪层
5. **追踪数据流**——坏值从哪来？一直追到源头。详见 `references/root-cause-tracing.md`

### Phase 2: 模式分析

1. 找同类能工作的代码
2. 完整读参考实现（不略读）
3. 列出所有差异
4. 理解依赖和环境假设

### Phase 3: 假设与测试

1. **单一假设**——"我认为 X 是根因，因为 Y"，写下来
2. **最小验证**——一次一个变量，最小改动
3. **验证后继续**——有效→Phase 4，无效→新假设，不在旧假设上叠加新修

### Phase 4: 实现

1. **先写失败测试**（TDD）
2. **单点修复根因**
3. **验证**——测试通过？其他测试没坏？
4. **修复失败？** <3 次回到 Phase 1；≥3 次停下来质疑架构

### 根因防御纵深

修完 bug 后，在数据经过的每一层加验证，让 bug 结构上不可能再发生。详见 `references/defense-in-depth.md`

## 七、Verification Before Completion · 证据先于声明

**声明完成之前，跑验证命令，确认输出。没有证据 = 撒谎。**

### 清单

- [ ] 跑了测试，全部通过
- [ ] 跑了构建/lint，无错误无警告
- [ ] 手动验证了关键路径（如果适用）
- [ ] 没有跳过任何验证步骤

### Red Flag

- "应该没问题" → 跑一下确认
- "我之前手动试过" → 自动化测试在哪
- "小改动不需要验证" → 小改动也引入 bug
- "测试跑起来太慢" → 至少跑相关的

## 八、Code Review 纪律

### 审查方

- 拿精简的上下文，不看审查对象以外的历史
- 两阶段：先 spec 合规（是否按规格建了），再代码质量（建得好不好）
- **顺序不可颠倒**

### 被审查方

- 技术评估，不是情绪表演
- 验证后再实现，不盲从
- 不理解就问，不确定就验证
- 合理的反对要表达

## 九、Git Worktree · 隔离工作

**功能开发用 worktree，不动主分支。**

- 新建 worktree 在独立目录
- 先确认基准测试通过
- 完成后三选一：merge / PR / keep
- 清理 worktree

## 十、Writing Skills · Skill 本身就是 TDD

写 skill = TDD 应用于流程文档：

1. 写压力场景（用子 agent 测试）
2. 看它失败（基线行为）
3. 写 skill 文档
4. 看测试通过（agent 遵守了）
5. 重构（堵漏洞）

详见 `skill-creator` skill。

## 通用 Red Flag 清单

| 想法 | 停下来 |
|------|--------|
| "太简单不需要流程" | 最简单的项目，未审视假设造成最大浪费 |
| "先做再调查" | 第一刀设模式，一开始就对 |
| "一次修多个" | 无法隔离哪个有效 |
| "跳过测试，我手动验证" | 手动不可复现 |
| "我看到问题了，修一下" | 看到症状 ≠ 理解根因 |
| "再试一次"（已失败2+） | 3次修不好，质疑架构 |
| "保留代码当参考" | 删。从测试重来。 |
| "这个 skill 过度了" | 简单变复杂最快。用它。 |
| "我知道这个 skill 的内容" | skill 会演进。读当前版本。 |
| "先做这一件小事" | 做任何事之前先查 skill |
